  ZMAN — RAILWAY DEPLOY (its own project, alongside dad's site)
══════════════════════════════════════════════

GOAL: Run Zman on the Railway you bought WITHOUT touching dad's site.

KEY IDEA: In Railway, each PROJECT is fully isolated — its own build, its own
variables, its own domain, its own volume. Two separate projects can never
override each other. So the rule is simply:

  → Create a NEW, SEPARATE Railway project for Zman.
  → Do NOT add Zman as a service inside dad's existing project.
  → Do NOT reuse dad's domain, secrets, or GitHub auto-deploy hook.

──────────────────────────────────────────────
  1. SECRETS — generate FRESH ones (never reuse dad's)
──────────────────────────────────────────────
Do NOT paste secrets that live in any other project. Generate new ones.

PowerShell:
  # AUTH_SECRET (any long random hex)
  [Convert]::ToHexString((1..32 | %{ Get-Random -Max 256 })).ToLower()
  # ENCRYPTION_KEY (must be exactly 64 hex chars)
  [Convert]::ToHexString((1..32 | %{ Get-Random -Max 256 })).ToLower()

Node (anywhere):
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

──────────────────────────────────────────────
  2. VARIABLES — paste into the NEW Zman project → Variables
──────────────────────────────────────────────
AUTH_SECRET=<fresh value from step 1 — unique to this project>
# NOTE: AUTH_SECRET also signs session tokens, which now carry a tokenVersion.
# Changing it logs everyone out — that is expected, not a bug.

# Comma-separated user IDs allowed to hit /api/admin/*. Leaving this unset
# disables the admin routes entirely (they fail closed — 403 for everyone).
ADMIN_USER_IDS=<your user id, e.g. from data/auth/users.json>

# AI provider + model (server-wide default — one key for everyone).
# ONE model per conversation. Do not reintroduce per-message model routing:
# prompt caches are keyed per model, so alternating models misses the cache on
# roughly every other turn, and re-writing the multi-thousand-token static
# prefix costs more than the cheaper model saves.
AI_PROVIDER=anthropic
AI_MODEL=claude-sonnet-5
ANTHROPIC_API_KEY=sk-ant-...
#
# ‼️ AI_MODEL_SIMPLE IS NO LONGER READ. The tiered Haiku/Sonnet routing was
#    removed (see the note above). Delete the variable from Railway — leaving it
#    set does nothing, but it will mislead the next person reading this file.
#
# ── Claude Sonnet 5 notes (why max_tokens is what it is) ────────────────────
# • Adaptive thinking is ON by default on Sonnet 5, and `max_tokens` caps
#   thinking PLUS the visible reply. The old 2048 was sized for a non-thinking
#   model and truncates answers here. The code now sends 8192; override with
#   ANTHROPIC_MAX_TOKENS if a workload needs more.
# • Chat turns send output_config.effort. It defaults to "medium" and NOT "low",
#   because effort has to match who is doing the thinking: while SCHEDULER_V2 is
#   off the model still works out slot placement itself, and "low" is meant for
#   short, scoped, non-intelligence-sensitive turns. Once the engine owns
#   placement the model only has to understand Hebrew and paraphrase reasons it
#   was handed — then AI_EFFORT=low is the honest setting and saves real money.
# • temperature / top_p / top_k are REJECTED by Sonnet 5 (400). None are sent —
#   do not add them.
# ANTHROPIC_MAX_TOKENS=8192               # optional override
# AI_EFFORT=medium                        # low | medium | high | xhigh | max
#
# ‼️ MiniMax, OpenRouter, the OpenAI *chat* path, and per-user API keys have all
#    been deleted from the code. MINIMAX_API_KEY / OPENROUTER_API_KEY are read by
#    nothing — delete them from Railway. OPENAI_API_KEY is still REQUIRED, but
#    only for voice transcription (see below), never for chat.
#    ENCRYPTION_KEY is likewise no longer read: it existed to encrypt per-user
#    API keys, and there are none. Safe to delete.

# ── SCHEDULER_V2 — ⚡ ON IN PRODUCTION since 2026-08-14 ──────────────────────
# Routes scheduling through the deterministic engine in src/lib/scheduling
# instead of letting the model do free-slot arithmetic. When set:
#   • get_free_slots is removed from the tool list entirely
#   • schedule_item / apply_plan appear (propose, then confirm — two phase)
#   • break_down_task and move_event become engine front-ends
#   • recurring create_event checks every instance and reports clashes
# UNSET = the previous behaviour, byte for byte. Only "1" or "true" turns it on.
# It is now SET on Railway (project truthful-love, service zman), so the engine
# path is the live one. To roll back it is a variable change, not a redeploy. Note plans are held in process memory for ~10 minutes, so
# a redeploy between a proposal and its confirmation makes the user re-ask.
SCHEDULER_V2=1

# ── PROJECTS — ⚡ ON IN PRODUCTION since 2026-08-14 ─────────────────────────
# Turns on the projects layer: a third mobile tab, a Tasks/Projects toggle in the
# desktop panel, and a full-screen board. When set:
#   • /api/projects and /api/projects/health start being read by the UI
#   • each project card shows four signals — deadline risk, progress, next step,
#     time invested — where the risk number comes from a dry run of the REAL
#     scheduling engine, so the board can never disagree with the calendar
#   • the board's shape follows the user's scheduling_method (BOARD_RULES), so a
#     Kanban user gets a WIP cap and a Deep Work user gets a one-block board
# UNSET = the app renders exactly as before. Only "1" or "true" turns it on.
# It is now SET on Railway alongside SCHEDULER_V2, which is what plan_project needs.
#
#   • the assistant gains create_project / list_projects / update_project /
#     delete_project, and — only when SCHEDULER_V2 is ALSO on — plan_project,
#     which schedules a whole project at once so dependencies and deadlines
#     resolve against each other. plan_project needs both flags because it
#     returns a plan_id that only apply_plan (a V2-only tool) can commit.
#
# Note the REST routes themselves are live and unflagged — they are authenticated
# and additive, and a route you cannot exercise in production is a route you
# cannot verify. The UI and the AI tools are what the flag gates.
#
# The engine's dependency support (Task.depends_on) ships unconditionally: with no
# dependsOn present it is a proven no-op, asserted by an identity test.
PROJECTS=1

# ── Voice transcription (OpenAI — this is the ONLY thing OPENAI_API_KEY is for)
OPENAI_API_KEY=sk-...
# Defaults to gpt-4o-transcribe, which is markedly better on Hebrew than the old
# whisper-1. Falls back to whisper-1 automatically if the model is unavailable.
# TRANSCRIBE_MODEL=gpt-4o-transcribe

# ── NOTIFICATIONS ‼️ Without the two below, NOTHING is ever delivered ─────────
# The notification feature has never actually fired: the cron endpoint is only
# reachable with CRON_SECRET, and nothing was calling it at all. Both are needed.
#
# 1. The secret the cron caller must present:
CRON_SECRET=<any long random string>
#
# 2. Then point a scheduler at it every 5 minutes (cron-job.org, or a Railway
#    cron service) — the app does NOT schedule itself:
#      GET https://<your-zman>.up.railway.app/api/cron/notifications?secret=<CRON_SECRET>
#
# 3. Delivery channel. ntfy needs no account and no keys: install the ntfy app,
#    subscribe to your topic, done. The topic is derived per-user by HMAC so it
#    is unguessable — anyone who learns a topic can publish to it, which is why
#    it is never derived from anything human-readable. With this unset, delivery
#    falls back to FCM (needs FIREBASE_SERVICE_ACCOUNT) or browser web-push.
NTFY_TOPIC_SECRET=<any long random string — changing it changes every topic>
# NTFY_SERVER=https://ntfy.sh          # override for a self-hosted ntfy

# Web push (browser PWA). Optional — only reaches a browser tab the user has
# open, so it is not a substitute for ntfy. Generate with:
#   npx web-push generate-vapid-keys
NEXT_PUBLIC_VAPID_PUBLIC_KEY=<vapid public>
VAPID_PRIVATE_KEY=<vapid private>

# URLs — fill in AFTER the first deploy gives you this project's own URL:
NEXT_PUBLIC_APP_URL=https://<your-new-zman>.up.railway.app
CAPACITOR_SERVER_URL=https://<your-new-zman>.up.railway.app

# Optional (native push): FIREBASE_SERVICE_ACCOUNT=<service-account JSON>

──────────────────────────────────────────────
  3. VOLUME — ‼️ REQUIRED, or ALL user data resets every deploy ‼️
──────────────────────────────────────────────
EVERYTHING the app remembers lives in files under one folder:
  - login accounts (you get logged out without this)
  - calendar events, tasks, profiles
  - the AI's MEMORY about each user
The container filesystem is ephemeral — it is wiped on every deploy/restart.
A mounted Volume is the ONLY thing that makes it survive.

New Zman project → Volumes → Add Volume → Mount Path: /app/data
(This volume belongs to the Zman project only. Dad's data lives in his own
project/volume — they never mix.)

If Railway can only mount the volume at a DIFFERENT path (e.g. /data), then set:
  DATA_DIR=<the volume's mount path>
and the app stores everything there instead. No need to match /app/data exactly.

VERIFY IT WORKED — two ways:
  1. Deploy logs show:  [storage] DATA_DIR=/app/data (writable)
     (must be the SAME path as the volume mount)
  2. Register an account → redeploy → if you're still logged in and your
     events/memory are still there, the volume is correct. If you got logged
     out, the volume is NOT mounted at the path the app uses.

──────────────────────────────────────────────
  4. STEPS
──────────────────────────────────────────────
1. railway.app → Login → New Project → Deploy from GitHub repo → select Zman's
   repo (alon0581/zman). This is a DIFFERENT project from dad's site.
2. Variables → paste everything from step 2 (using fresh secrets from step 1).
3. Volumes → Add Volume → Mount Path: /app/data.
4. Deploy. Copy the generated URL.
5. Set NEXT_PUBLIC_APP_URL and CAPACITOR_SERVER_URL to that URL → redeploy.
6. (Native apps only) rebuild with CAPACITOR_SERVER_URL set so the iOS/Android
   shell loads this Zman project, not any other.

──────────────────────────────────────────────
  WHY THEY WON'T OVERRIDE EACH OTHER
──────────────────────────────────────────────
• Separate projects = separate builds, env vars, volumes, domains.
• Railway's GitHub auto-deploy is configured PER service: dad's service watches
  dad's repo/branch; Zman's service watches Zman's repo/branch. Don't point both
  services at the same repo and you're safe.
• If you use custom domains, give each project a DIFFERENT domain.
